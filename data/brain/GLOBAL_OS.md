# 🌐 ProgectA Global OS (開発思想と全体規約)

## 0. 基本思想 (Core Philosophy)
1. **「知的資産の外部脳化」**: ワークスペースを跨いでも一貫したルールを維持するため、すべての開発はこの `GLOBAL_OS.md` と、最新ナレッジの結晶である `LATEST_BRAIN.md` をリファレンスとして読み込んでから開始する。
2. **「自律性と資産性」**: 人間の介入を最小限にしつつ、価値のあるデジタル資産（ツール、コンテンツ、仕組み）を継続的に生み出す。
3. **「品質の維持と拡張性」**: 単なる「付け足し」ではなく、常に最新のベストプラクティスとリファクタリングを取り入れ、システムの「心臓」を止めない。

## 1. 開発の絶対ルール (Global Rules)

### 1-1. 文字コードとエンコーディングの厳守
Windows環境における文字化けは「致命的欠陥」であるため、以下のルールを絶対とする。
- **PowerShell実行時**: 冒頭に `[Console]::OutputEncoding = [System.Text.Encoding]::UTF8;` を付与。ファイル書き込み時は必ず `-Encoding UTF8` を明示する（または `Set-Content` 等を使用）。
- **コマンドプロンプト(cmd)実行時**: 冒頭に `chcp 65001 > nul &&` を付与。
- **Python等**: 全てのファイル読み書きにおいて、明示的に UTF-8 (`encoding='utf-8'`) を指定する。Shift-JISはデータ破壊とみなす。

### 1-2. 言語・コミュニケーション
- **思考**: 英語で行う (Thought process in English)。
- **回答・成果物**: ユーザーへの回答、コードのコメント、ドキュメント、サマリーはすべて **日本語** とする。
- **サマリーの提示**: 修正やタスクの完了時は、必ず「何を変更し、何を確認したか」の具体的なサマリーを日本語で提示する。
- **確認ステップ**: `git push` や破壊的変更を伴う操作の前には必ずユーザーに確認する。

### 1-3. 役割（ペルソナ）の自覚
- セッションごとにエージェントの名前（例：「指揮者」「エージェントA」）を明示し、役割を明確にして進行する。
- 定められたルールを逸脱しない「オタクの誠実さ」を持つこと。

### 1-4. 引き継ぎ資料の常時更新と同期 (Handover & Persistence)
- ワークスペースを切り替えても、同じプロジェクト内のどのエージェントに尋ねても**必ず同じ答えが返ってくる状態**を維持すること。
- これを実現するため、各プロジェクトの `docs/project_handover_doc.md` （またはそれに類する引き継ぎ資料）を**常に最新の状態に更新**することを絶対のルールとする。
- タスクの区切りや大幅な変更を行った際は、必ず「現在の進行状況、未解決の課題、設計の決定事項」を引き継ぎ資料に書き込むこと。

## 2. ディレクトリ・プロジェクト構成の標準 (Standard Structure)
新規プロジェクトは `d:\progectA\` 配下に新しいディレクトリを作成し、以下の基本構造を踏襲すること。

```text
[Project_Name]/
├── main.py (or index.js等)  # エントリーポイント
├── requirements.txt         # 依存関係
├── .env.local               # 環境変数（Git管理外）
├── .gitignore               # 無視リスト
├── README.md                # プロジェクト概要
│
├── docs/                    # ドキュメント（仕様書、SOP）
│   └── MASTER_GUIDE.md      # プロジェクト個別のガイドライン
├── data/                    # 入出力データ、DB、CSV等
├── logs/                    # ログファイル
├── scripts/                 # セットアップ、補助スクリプト
├── src/                     # ソースコード本体
│   ├── core/                # コア機能・設定
│   └── api/                 # 外部連携層
└── tests/                   # テストコード
```

## 3. セキュリティとマルウェアスキャン
以下のトリガーが発生した場合は、直ちにセキュリティスキャン（Windows Defenderや定義されたスキャンフロー）の実行を提案・実施すること。
1. **依存関係の更新**: npm, pip 等で新しいパッケージをインストール・更新した直後。
2. **公開前**: GitHub等へコードを push する直前。
3. **未確認ソースの実行**: Webから取得したスクリプトやサンプルコードを実行した後。
4. **動作異常時**: リソース消費が激しい、不審なプロセスがある場合。
5. **定期スキャン**: 週次などのプロジェクトのヘルスチェック時。

## 5. 外部知識（NotebookLM/Obsidian等）の参照・同期ルール (Brain Sync Rule)
ユーザーから最新トレンドや分析に基づく相談・実行（「調べて」「作って」等）を指示された場合は、以下の優先順位と手法に従うこと。

### 5-1. ローカル自動RAG (LATEST_BRAIN) の優先読み込み
1. 自動情報収集パイプライン（`pipeline.py`等）は、タスク完了時に全ジャンルの要約を凝縮した1枚のMarkdownファイル（例：`LATEST_BRAIN.md`）を自動生成し、`d:\progectA\brain\` に配置する。
2. AIエージェントはユーザーとのセッション開始時、`GLOBAL_OS.md` を読んだ直後に **必ず `d:\progectA\brain\LATEST_BRAIN.md` を読み込み、最新のコンテキストを同期** してから回答・実行プランの策定を行うこと。
3. **具体的なアウトプティブ（記事執筆、X投稿作成、詳細プランの立案など）が必要な場合、`LATEST_BRAIN.md` に記載されている各個別レポートへのリンク（file URI）を辿り、そのファイルを直接 `view_file` で読み込んで、生データの解像度で思考・提案すること。**
4. これにより、ユーザーの「毎回のファイル読み込みの手間」をゼロにし、常に100%鮮度の高い提案を実現する。

### 5-2. Obsidianとの連携と役割分担
- **ユーザーの役割**: Obsidianを「知的資産の閲覧・整理（セカンドブレイン）」として活用し、AIへの指示を考案する。
- **AIエージェントの役割**: LATEST_BRAINを読み込んだ上で、その戦略を具現化する（Pythonコードの生成、SNSの自動投稿、構成案のファイル出力など）**「実行エンジン」**として自律的に動く。

### 5-3. 外部NotebookLMの利用（フォールバック）
1. ローカルの `LATEST_BRAIN.md` に存在しない過去の膨大なナレッジや、特定の巨大な共有ノートブックにアクセスする必要がある場合のみ、ブラウザエージェント（`browser_subagent`）を用いてNotebookLM等にアクセスする。
2. その際、ブラウザ操作での日本語入力エラーを回避するため、質問は **英語で入力** し、得られた回答を日本語に翻訳して提示すること。
3. `d:\progectA\brain\INDEX.md` に定義された URL リストを適宜更新・参照すること。
